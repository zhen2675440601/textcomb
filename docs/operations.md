# 部署与运维

## 上线前

- 将 `TEXTCOMB_PUBLIC_ORIGIN` 设为唯一 HTTPS 站点源，例如 `https://textcomb.example.com`，不得带路径。
- 将 `TEXTCOMB_SECURE_COOKIES` 设为 `true`。
- 使用密码管理系统保存 PostgreSQL 密码和 32 字节主密钥；不得提交 `.env`。
- 主密钥丢失后模型密钥无法恢复。轮换主密钥需要先实现逐条重加密流程，不能直接替换。
- 只开放 Caddy 端口。PostgreSQL、API、Worker 和假模型不得直接暴露到互联网。
- 为宿主机、容器镜像、TLS、数据库备份和安全更新建立责任人。

## 健康与指标

- `/healthz`：进程存活。
- `/readyz`：数据库可查询。
- `/metrics`：Prometheus 文本格式。不得把该端点公开给未授权互联网用户。

结构化日志只应出现请求 ID、用户 ID、任务 ID、阶段、耗时、用量和错误码。正文、问题片段、密码、Cookie、模型密钥和完整提示词禁止进入日志。

建议告警：

- 队列最老等待时间持续超过 10 分钟；
- 任务失败率或模型 429/5xx 重试率突增；
- 租约恢复次数非零；
- 任务 P95 超过 60 分钟或逼近 120 分钟强制超时；
- 清理任务连续失败；
- PostgreSQL 或共享存储剩余空间不足 20%。

120 分钟默认强制超时从创建任务起计算，包含排队等待。已过期的排队任务直接标为 `failed`（错误码 `JOB_TIMEOUT`），不会调用模型；租约恢复不延长截止时间。主动重试会重新设置截止时间，同时保留原有模型与提示词快照。

## 数据生命周期

- 上传或粘贴正文时，原文件／临时 TXT 和失败重试数据的过期时间均为 24 小时；失败任务到期后清除文件、文本块和完整提取正文，无有效报告关联的正文不继续保留。
- 成功后立即清除原始上传文件；提取后的“分析原文”仅用于报告定位，随报告保留。取消或用户删除会立即清除原文件与完整正文；文件系统删除失败时保留待清理路径并每小时重试。
- 报告、分析原文、问题片段和审核反馈默认 180 天后删除。PDF 按下载请求临时生成，用毕即删除；旧版已保存的 PDF 随报告过期清理。
- 文档、任务与报告删除都要求全部关联任务已结束；`cancel_requested` 不算已结束，必须等到 `cancelled`。遇到并发新建或重试造成的冲突，应刷新后确认状态，不要绕过 API 直接删除文件。
- 用户主动删除报告会同步删除分析原文、问题与反馈；任务只保留不含正文的最小状态元数据并标记 `expired`。旧库中若有其他报告或失败任务共享同一文档，正文仅为报告定位/失败重试保留；最后一个使用者删除后立即清理，仅有状态元数据不阻止清理。
- 匿名统计只能保留类别与反馈结果，不能保留原文片段。

## 备份与恢复

备份 PostgreSQL、账户数据和仍在保留期内的报告卷。不要备份 `uploads/` 或 `tmp/`；数据库中的 `documents.extracted_text` 属于报告关联原文，备份保留期限不得超过报告保留期，并且删除策略执行后不得在长期备份中重新出现已删除原文。

恢复演练至少验证：迁移可前滚、会话可失效、报告 JSON/Markdown/PDF 一致、过期清理继续工作。恢复环境必须使用与备份匹配的主密钥。

隔离演练时先停止 API/Worker 写入，使用 `pg_dump --format=custom` 创建数据库快照，并用 `pg_restore --exit-on-error` 恢复到新建的独立空库，不覆盖在线数据库。模型配置密文与数据库一起恢复；对应主密钥单独提供，不放在快照旁或 Release 制品中。将演练服务的 `TEXTCOMB_DATABASE_URL` 明确指向恢复库；不要误用无效的 `DATABASE_URL` 变量后仍连接旧库。CLI 重新执行 `migrate` 应成功且不重复应用迁移。

比较账户、模型配置、文档、任务和报告等表数量，再通过 API 核对同一报告的 JSON、Markdown、PDF 内容和原文窗口；PDF 可以重新渲染，不能仅用文件哈希判断语义一致。恢复前后都应拒绝其他用户读取报告。重新开放恢复环境前，通过受控管理员连接清空恢复库的 `sessions`，确认旧会话返回 401，再重新登录；不得删除原生产库的会话作为演练步骤。使用恢复后的加密配置做合成内容连接测试，确认主密钥匹配。最后验证过期清理和十任务受控并发；假模型只验证工程行为，不证明语言质量或真实服务吞吐。

## 版本升级

1. 备份数据库与报告卷。
2. 拉取固定版本镜像，不使用未锁定的 `latest`。
3. 单独运行 `textcomb-cli migrate`。
4. 先启动 API 并检查 `/readyz`，再启动 Worker，最后切换 Caddy。
5. 观察失败率、队列和租约恢复；若应用回退，数据库迁移仍保持前滚兼容。
