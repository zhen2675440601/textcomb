# 架构说明

TextComb 是模块化单体。API 与 Worker 使用同一套 Rust 领域模块和 PostgreSQL，不引入 Redis，也不把早期项目拆成微服务。

```text
浏览器 ── Caddy ── API ───────── PostgreSQL
                    │                 ▲
                    └── 共享存储      │ SKIP LOCKED＋租约
                          ▲           │
                          └──────── Worker ── 可配置模型协议
                                      ├── OpenAI Responses
                                      ├── OpenAI Compatible
                                      ├── Anthropic Messages
                                      ├── Poppler
                                      └── Typst＋Noto CJK
```

## 任务生命周期

1. API 接收上传文件或直接粘贴的 UTF-8 正文；前者校验扩展名、MIME、文件签名和 20 MiB 上限，后者校验非空与 20 万字上限。两者都会以随机 UUID 写入私有存储，并沿用相同的分析、定位和清理链路。
2. Worker 使用 `FOR UPDATE SKIP LOCKED` 原子领取未过期任务，写入两分钟租约，并每 30 秒续租；领取时将排队中已过截止时间的任务标为 `failed`（错误码 `JOB_TIMEOUT`），不进入解析或模型调用。失去租约后停止本地模型调用和写入，避免旧 Worker 覆盖接管者的结果。
3. 解析器建立不可变提取正文与来源映射。分析只使用字符下标，不信任模型提供的绝对位置。跨页问题的 `SourceLocation` 保留起始 `page`、可选结束 `page_end` 及两端行号；该新增字段在旧 `ReportV1` 中可缺失，无法恢复结束页的旧逆序行号不再显示为同页范围。
4. 按完整段落生成约 3000 字、最多 4000 字文本块；块包含前后文重叠区，但只允许报告核心区的问题。超长段落在句末标点附近切分，核心区互不重叠。
5. 任务创建时冻结通用、学术论文或财报场景的最终提示词；第一轮模型先结合上下文检查句子成分、指代、否定、逻辑与关联关系，再为具体疑点归类。复核只接收原文和待检查位置，独立判断类别。论文场景保护引用编号和 DOI，财报场景保护金额、比例和日期；错字、标点命中保护片段时降为疑似，病句仅当问题片段整体位于受保护内容内时降级。服务器必须把原文引用唯一定位，否则丢弃。
6. 第二轮模型只复核存在候选的文本块，并独立判断。80–100 为正式问题，50–79 为疑似，低于 50 丢弃；分段、受保护片段以及表意不明、不合逻辑、用词不当永远是疑似。
7. 合并同类型、重叠位置且建议相同的问题，生成唯一 `ReportV1`，记录活动依据 ID 与修订号的 SHA-256 版本指纹，并先完成在线报告；导出时将作者的判断和漏检反馈附加到报告对象，JSON、Markdown 和 PDF 从该对象生成。旧报告可能没有依据库版本字段。PDF 按需渲染，失败只影响该次 PDF 下载。
8. 成功后清除文本块内容、模型原始输出和原始上传文件，提取正文作为“分析原文”随报告保留 180 天；取消后立即清除正文和原文件。取消监控会中断正在等待重试的模型请求。

任何一个文本块失败，整篇任务进入 `failed`。重试会验证切块边界和锁定提示词版本，复用已完成块，仅运行失败、未完成或输出损坏的块。

任务截止时间从创建时计算，包含排队时间。Worker 只使用剩余时间，崩溃接管不会重置截止时间；用户主动重试才重新计算截止时间。

## 一致性与并发

- `(user_id, idempotency_key)` 防止重复创建分析任务。
- 一个上传文档只创建一个分析任务；失败时重试原任务，避免取消或完成一个任务时清理另一个任务仍需使用的原文。
- Worker 领取使用行锁跳过已锁任务；租约过期可恢复排队。
- 每个任务默认最多并行两个块，全局模型调用默认 10，并叠加同一模型配置的动态并发限额。每次发起模型调用前读取当前限额；降低限额不打断已开始的请求，待其自然结束后才放行新的请求，等待者每秒检查上调。该限额与全局限额均为单 Worker 进程内限额，多 Worker 部署需自行分配总预算，不能视为跨进程全局配额。
- 报告、问题和任务终态在一个数据库事务内提交；不完整报告不会标记完成。
- 报告提交先锁定任务并校验当前 Worker；取消清理必须在同一事务中确认 Worker 归属和 `cancel_requested/cancelled` 状态。租约失效属于冲突，不得误作用户取消。
- 文档、任务和报告删除共用同一入口：按报告、任务、文档的顺序锁定全部关联资源，持锁检查终态并删除。关联任务处于运行、排队或 `cancel_requested` 时一律返回冲突；重试或 Worker 领取不能插入到状态检查与文件删除之间。与新建任务并发时重新核对关联集合，发生变化则拒绝删除。兼容旧库中共享文档的多个任务，其他关联报告或失败重试仍需正文时保留；仅有已过期/取消的状态元数据不阻止正文清理。
- 迁移只由一次性 CLI 执行。字段删除至少跨一个版本，迁移只前滚。

## 模块边界

- `textcomb-domain`：无基础设施依赖的公共类型和版本化报告。
- `textcomb-core::documents`：格式识别、资源限制、正文提取和位置映射。
- `textcomb-core::analysis`：切块、唯一定位、置信度分层和去重。
- `textcomb-core::provider`：统一 Provider trait、协议工厂（OpenAI Responses、OpenAI Compatible、Anthropic）、重试和 JSON 修复。
- `textcomb-core::db`：队列租约、持久化、清理和报告事务。
- `textcomb-core::worker`：编排，不承载 HTTP 逻辑。
- `textcomb-api`：认证、资源所有权、SSE、管理和导出。

## 明确不做

首版不做 OCR、全文改写、事实核查、论文格式、全文一致性、专业术语承诺、支付或小程序。商业版和小程序只能复用现有 API 与领域类型，不能把计费逻辑放进客户端。
