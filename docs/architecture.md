# 架构说明

TextComb 是模块化单体。API 与 Worker 使用同一套 Rust 领域模块和 PostgreSQL，不引入 Redis，也不把早期项目拆成微服务。

```text
浏览器 ── Caddy ── API ───────── PostgreSQL
                    │                 ▲
                    └── 共享存储      │ SKIP LOCKED＋租约
                          ▲           │
                          └──────── Worker ── 可配置模型协议
                                      ├── OpenAI Responses
                                      ├── OpenAI Compatible
                                      ├── Anthropic Messages
                                      ├── Poppler
                                      └── Typst＋Noto CJK
```

## 任务生命周期

1. API 接收上传文件或直接粘贴的 UTF-8 正文；前者校验扩展名、MIME、文件签名和 20 MiB 上限，后者校验非空与 5 万字上限。两者都会以随机 UUID 写入私有存储，并沿用相同的分析、定位和清理链路。
2. Worker 使用 `FOR UPDATE SKIP LOCKED` 原子领取任务，写入两分钟租约，并每 30 秒续租；失去租约后停止本地模型调用和写入，避免旧 Worker 覆盖接管者的结果。
3. 解析器建立不可变提取正文与来源映射。分析只使用字符下标，不信任模型提供的绝对位置。
4. 按完整段落生成约 3000 字、最多 4000 字文本块；相邻块最多重叠一个 500 字段落。
5. 第一轮模型先结合上下文检查句子成分、指代、否定、逻辑与关联关系，再为已成立的问题归类；服务器必须把原文引用唯一定位，否则丢弃。
6. 第二轮模型独立复核整块候选。80–100 为正式问题，50–79 为疑似，低于 50 丢弃；分段、受保护片段以及表意不明、不合逻辑、用词不当永远是疑似。
7. 合并同类型、重叠位置且建议相同的问题，生成唯一 `ReportV1`，再从同一个对象导出 JSON、Markdown 和 PDF。
8. 成功后清除文本块内容、模型原始输出和原始上传文件，提取正文作为“分析原文”随报告保留 180 天；取消后立即清除正文和原文件。取消监控会中断正在等待重试的模型请求。

任何一个文本块失败，整篇任务进入 `failed`。重试会验证切块边界和锁定提示词版本，复用已完成块，仅运行失败、未完成或输出损坏的块。

## 一致性与并发

- `(user_id, idempotency_key)` 防止重复创建分析任务。
- Worker 领取使用行锁跳过已锁任务；租约过期可恢复排队。
- 每个任务默认最多并行两个块，全局模型调用默认 10，并叠加同一模型配置的并发信号量。
- 报告、问题和任务终态在一个数据库事务内提交；不完整报告不会标记完成。
- 迁移只由一次性 CLI 执行。字段删除至少跨一个版本，迁移只前滚。

## 模块边界

- `textcomb-domain`：无基础设施依赖的公共类型和版本化报告。
- `textcomb-core::documents`：格式识别、资源限制、正文提取和位置映射。
- `textcomb-core::analysis`：切块、唯一定位、置信度分层和去重。
- `textcomb-core::provider`：统一 Provider trait、协议工厂（OpenAI Responses、OpenAI Compatible、Anthropic）、重试和 JSON 修复。
- `textcomb-core::db`：队列租约、持久化、清理和报告事务。
- `textcomb-core::worker`：编排，不承载 HTTP 逻辑。
- `textcomb-api`：认证、资源所有权、SSE、管理和导出。

## 明确不做

首版不做 OCR、全文改写、事实核查、论文格式、全文一致性、专业术语承诺、支付或小程序。商业版和小程序只能复用现有 API 与领域类型，不能把计费逻辑放进客户端。
